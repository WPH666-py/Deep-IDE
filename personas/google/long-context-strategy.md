# Gemini Persona — 长上下文分析策略

## Gemini 1M Token 上下文窗口的高效使用

### 1. 注意力分布科学

LLM 的注意力在不同位置有显著差异：

```
[前10%]   ████████████  最高注意力  →  放任务说明、关键约束
[10-30%]  ████████░░░░  高注意力    →  放核心接口/类型定义
[30-70%]  ████░░░░░░░░  中注意力    →  放实现文件（按模块组）
[70-90%]  ██████░░░░░░  回升注意力  →  放测试文件、配置文件
[90-100%] ████████████  恢复注意力  →  放输出格式要求、Checklist
```

### 2. 分段分析策略

对于超大代码库（>500K tokens）：

```
Step 1: 摘要扫描
  "只读每个文件的 exports、interfaces、type definitions，给我项目结构概览"

Step 2: 关键深度分析
  "基于概览，深入分析以下3个关键模块：[module_a], [module_b], [module_c]"

Step 3: 交叉验证
  "交叉检查 module_a 的接口是否在 module_b 中被正确调用"

Step 4: 全局整合
  "基于所有分析，给出完整的架构理解和改进建议"
```

### 3. 上下文组织的四种模式

```
模式1: 逐模块组织（适合功能开发）
=== MODULE: Authentication ===
[所有 auth 相关文件]

=== MODULE: Database ===
[所有 db 相关文件]

模式2: 逐层组织（适合架构审查）
=== LAYER: API Routes ===
=== LAYER: Services ===
=== LAYER: Repositories ===
=== LAYER: Models ===

模式3: 逐变更组织（适合代码审查）
=== CHANGED FILES ===
[改动的文件完整内容]

=== REFERENCED FILES ===
[被引用的文件摘要]

模式4: 逐依赖组织（适合重构）
=== CORE DEPENDENCY ===
[被最多文件 import 的模块]

=== LEAF FILES ===
[最少被依赖的文件，可以安全修改]
```

### 4. 避免上下文污染

```
✅ DO:
  - 使用明确的 SECTION 标签分隔
  - 每个文件标注完整路径
  - 在任务前加上 "Based on the following files, ..."

❌ DON'T:
  - 把所有文件不加标签地堆在一起
  - 把不相关的文件混入上下文
  - 使用模糊的引用（"that file above" → 用具体路径）
```

### 5. 并行分析触发条件

当满足以下条件时使用并行分析：
- 需要审查 3+ 个独立文件
- 每个文件的分析不依赖其他文件的结果
- 时间敏感（需要快速返回结果）
